Real-world maps for a 2D/isometric tower-defense game

Research date: 13 September 2026. This is an initial technical assessment based on primary documentation; no area-specific data import or performance benchmark has been run. Proposed architecture and gameplay choices below are engineering recommendations.

The recommended starting point is OpenStreetMap geometry, with Overture buildings evaluated as an alternative building layer, converted into a stylized scene in Godot. A small 3D scene viewed through an orthographic camera should suit the isometric presentation. Keep gameplay navigation on a separate 2D representation.

The key distinction is between map images and map geometry. A satellite image supplies pixels; building footprints supply polygon coordinates that can become individual buildings, collision boundaries, and selectable targets. An outline plus an estimated height is enough for a recognizable stylized building. Accurate roofs, facades, gardens, and interiors require additional information or procedural approximation.

| Source or tool | What it supplies | Assessment for this game |
| --- | --- | --- |
| OpenStreetMap | Roads, paths, buildings, land use, water, and optional building detail | First choice for a coherent level and road network. Inspect coverage locally. |
| Overture Maps buildings | Consolidated footprints with optional heights, floors, and building parts | Compare against OSM; particularly useful where OSM buildings are sparse. |
| Google Photorealistic 3D Tiles | Streamed textured 3D geography | Useful for visualization experiments where available; poor basis for editable, offline level generation. |
| OSM2World | Conversion from OSM to 3D models | Fast route to a visual feasibility test; supports glTF/GLB export. |
| Blender + Blosm, using OSM | Import of buildings, roads, water, vegetation, and terrain | Useful for art experiments and inspecting one neighborhood. |
| MapLibre GL JS | Browser map rendering and extruded-building previews | Suitable for an area picker or lightweight visual prototype; map data hosting is a separate choice. |
| Copernicus DEM | Broad terrain elevation | Consider after a flat prototype; insufficient for garden walls and curbs. |

OSM supports building outlines, building parts, heights, levels, and roof tags, but these fields are not guaranteed everywhere. Its broader mapping data includes roads and paths. [OSM introduction](https://www.openstreetmap.org/about), [Simple 3D Buildings](https://wiki.openstreetmap.org/wiki/S3DB).

Overture combines OSM with additional authoritative and machine-derived sources. It already resolves overlaps between sources; combining all OSM and Overture buildings again would introduce duplicates. For an initial hybrid, use Overture buildings with OSM roads and land use, then inspect alignment. Heights and floor counts are optional, and some geometry represents roof outlines rather than ground footprints. [Building schema](https://docs.overturemaps.org/schema/reference/buildings/building/), [buildings guide](https://docs.overturemaps.org/guides/buildings/).

Google has an official streaming route through Map Tiles API and integrations such as Cesium for Unity. However, the API policies limit use to visualization and restrict extraction, offline use, and caching. The standard and EEA terms restrict creating content from Google Maps content. These are material obstacles to tracing imagery, extracting game geometry, or packaging Google-derived levels. A tool being able to import data does not establish permission to redistribute it. [Map Tiles policies](https://developers.google.com/maps/documentation/tile/policies), [standard terms](https://cloud.google.com/maps-platform/terms), [EEA terms](https://cloud.google.com/terms/maps-platform/eea), [Cesium for Unity](https://cesium.com/learn/unity/).

For a new project linked to an EEA billing account, Google explicitly says Photorealistic 3D Tiles and satellite image tiles in the Map Tiles API are unavailable. The rule applies to new projects after 8 July 2025 and certain modified existing integrations. If billing in Romania, this matters directly. Google's native 3D Maps products are listed as alternatives, but do not provide unrestricted asset export. Google's former Maps gaming services were decommissioned on 31 December 2022; older Unity gaming-SDK tutorials are obsolete. [EEA API adjustments](https://developers.google.com/maps/comms/eea/map-tiles), [deprecations](https://developers.google.com/maps/deprecations).

Suggested conversion pipeline:

1. Select a center and rectangle in a map interface. Begin with a manually chosen area roughly 500 × 500 meters. Keep the data importer independent of the picker. An open-data picker avoids depending on Google content for level generation.
2. Fetch buildings, road/path lines, water, and land-use polygons, with a margin beyond the play boundary. Small OSM queries can use Overpass; regional PBF extracts support local processing later. Overture's Python client downloads a bounding box into GeoJSON or GeoParquet. Preserve source identifiers, timestamps/releases, and attribution alongside the data. [Overpass resource guidance](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html), [Geofabrik Europe extracts](https://download.geofabrik.de/europe.html), [Overture Python client](https://docs.overturemaps.org/getting-data/overturemaps-py/).
3. Convert longitude/latitude into a suitable local metric coordinate system and subtract a local origin. Use meters for building sizes and movement distances. Repair invalid geometry, handle polygon holes and multipolygons, and clip for rendering only after preserving required connectivity. Python's pyproj and Shapely cover coordinate conversion and geometry operations. [pyproj](https://github.com/pyproj4/pyproj), [Shapely manual](https://shapely.readthedocs.io/en/stable/manual.html).
4. Turn footprints into meshes: triangulated roof/top faces plus extruded walls. Prefer measured height; otherwise estimate from floors, then a documented building-type default. Label inferred values internally. Roads become widened strips, parks become ground surfaces, and water becomes a blocked area. Add seeded roof and facade variants for visual consistency between visits.
5. Generate gameplay separately: building obstacles, tower placement zones, a connected road graph, spawn candidates, and a target entrance. Connect the selected home to a reachable path; a pin at a building's center is usually inside an obstacle. Preserve bridge/tunnel separation instead of connecting every visually crossing line. Validate all spawn-to-target routes and prevent tower placements from sealing every route if the design requires continuous access.
6. Save a versioned level package: geometry/features, optional GLB visuals, navigation, target and spawn points, generator version, seed, source release, and license notices. Freezing inputs prevents a saved level changing when source maps update. Load the package into the engine, then add enemies and towers.

For the engine, Godot offers procedural meshes through ArrayMesh/SurfaceTool, orthographic cameras, and glTF/GLB import. My recommendation is simple 3D buildings with an angled orthographic camera and 2D navigation logic. This accommodates arbitrary street angles and building shapes while retaining an isometric appearance. A strict diamond tile grid would require quantizing the source geometry and could erase small alleys or distort the home. A fully 2D renderer remains possible using the same footprints; it adds decisions about projected walls and draw order. [Procedural geometry](https://docs.godotengine.org/en/stable/tutorials/3d/procedural_geometry/index.html), [Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html), [import formats](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html).

There are two useful prototypes. For a quick visual test, import one OSM extract into OSM2World or Blosm, export GLB, and inspect it in Godot. This proves recognition and art direction, but a rendered mesh alone does not supply the game's semantic data. For the actual selectable-area feature, build an automated converter that retains feature IDs, footprints, road connectivity, and buildability. A browser preview can use MapLibre's extrusion example. [OSM2World](https://osm2world.org/), [Blosm documentation](https://github.com/vvoovv/blosm/wiki/Documentation), [MapLibre 3D example](https://maplibre.org/maplibre-gl-js/docs/examples/display-buildings-in-3d/).

I would begin with flat terrain. Copernicus offers global 30 m and 90 m elevation products under its license, with access conditions depending on the distribution service. These are surface models and may include vegetation/buildings. They can inform broad slopes, but should not be treated as precise bare ground around each house. More detailed local elevation or municipal 3D data is a later, location-dependent option. [Copernicus DEM collection](https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM).

Open data also has obligations. OSM and Overture's buildings theme use ODbL. Plan for attribution and applicable sharing/access obligations for a derivative database, including when publicly used through a produced work. This does not automatically mean the game's source code must be open. Keep geographic data, its modifications, and independent game assets clearly identifiable. [OSM copyright](https://www.openstreetmap.org/copyright), [OSMF produced-work guidance](https://osmfoundation.org/wiki/Licence/Community_Guidelines/Produced_Work_-_Guideline), [Overture licensing](https://docs.overturemaps.org/attribution/).

Free data should also be distinguished from free production infrastructure. Public Overpass has resource limits. OSM's standard tile server prohibits bulk/offline downloads; use raw geographic extracts for level generation, and an appropriate provider or self-hosted tiles for the picker. Hosting, preprocessing, storage, and address search can incur costs even with open data. The first prototype can use manual map selection without geocoding. [OSM tile policy](https://operations.osmfoundation.org/policies/tiles/).

The most useful next experiment is three small areas: a dense urban block, a residential neighborhood, and a sparsely mapped area. Compare OSM and Overture building coverage, check that a user can identify the target home, and test route connectivity and available tower space. Record generation time, feature/triangle counts, and target-device frame rate. No performance numbers or coverage guarantees are established by this research.

Prototype success means selecting an area, generating a recognizable scene, selecting a home, placing towers, and routing one enemy wave to it. Include a local correction tool for missing homes or entrances. Real geography will need gameplay rules for overly short routes, isolated targets, excessive entrances, and unusable areas; those rules are likely to be a larger design challenge than the initial polygon-to-mesh conversion.
